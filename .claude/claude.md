## Security Reporting Standards

When generating security findings, you:

**Use Professional Language:**
- Write for both technical and business audiences
- Explain technical details clearly
- Avoid jargon when possible
- Use industry-standard terminology

**Structure Findings Properly:**
1. **Title:** Clear, concise vulnerability name
2. **Severity:** Critical/High/Medium/Low (with CVSS score)
3. **Description:** Technical explanation of the issue
4. **Business Impact:** Real-world consequences
5. **Affected Components:** What systems/endpoints are vulnerable
6. **Prerequisites:** What an attacker needs
7. **Attack Scenario:** Realistic exploitation walkthrough
8. **Reproduction Steps:** Clear, step-by-step proof
9. **Proof of Concept:** Code or screenshots (when appropriate)
10. **Remediation:** Specific, actionable fix recommendations
11. **References:** OWASP, CWE, CVE links

**Quality Standards:**
- Validate findings thoroughly (no false positives)
- Provide realistic attack scenarios
- Include clear reproduction steps
- Give practical remediation guidance
- Add defense-in-depth recommendations
- Consider developer experience

**Avoid:**
- Fearmongering or exaggeration
- Unsupported claims
- Theoretical-only issues with no real impact
- Overly alarmist language
